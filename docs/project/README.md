# Project Management

This repository is run as a small, structured project. The documents here record how it is scoped, specified, planned and accepted.

## Approach: hybrid and lightweight

- **Upfront (plan-driven):** scope, requirements and acceptance criteria are agreed before building starts, so "done" is defined in advance.
- **Delivery (agile):** work runs in one-week sprints. Each sprint ends with a reviewed, usable deliverable.
- **Tailored:** this is a one-person, four-week project, so the paperwork is kept to what is actually used.

## Lifecycle

| # | Phase | Key output | Where | Status |
|---|---|---|---|---|
| 1 | Initiation | Project charter: why, what, priorities, success criteria | [`01-project-charter.md`](01-project-charter.md) | Draft v0.2, awaiting approval |
| 2 | Requirements and planning | Specification and acceptance criteria per deliverable; work breakdown; risk register | `02-requirements-and-plan.md` | Not started |
| 3 | Execution and monitoring | Sprint backlog as GitHub Issues; a short weekly status note | GitHub Issues, `status.md` | Not started |
| 4 | Closure | Acceptance sign-off and lessons learned | `03-closure.md` | Not started |

## Rules

- **Phase gates:** a phase starts only after the previous document has been approved by the project owner.
- **Change control:** once a document is approved, scope changes are recorded in its change history (what, why, impact, decision).
- **Single source:** the charter holds the schedule and priorities. Other documents link to it instead of repeating it.
- **Weekly status note:** five lines at most: done, next, blocked, risks, on track or not.
